Current `main` HEAD alembic revision: `e8f9a0b1c2d3` (chain your new migrations off this — run `python -m alembic heads` first to confirm before writing `down_revision`, and make sure you end with a SINGLE head, no branch split).

Follow existing conventions exactly:
- Module layout: `src/pawguard/modules/<name>/{models,repository,service,router,schemas}.py`

## 1. Donation: sponsorship billing cycle

**Problem:** `DonationType.SPONSORSHIP` exists as an enum label only — a sponsorship donation is currently indistinguishable from a one-time donation. PRR 3.11 requires: donor commits **monthly** funding to a **specific animal**, and the system auto-routes monthly progress updates to the sponsor.

**Build:**
- New model `DogSponsorship` (`src/pawguard/modules/donation/models.py`): `donor_id` FK, `dog_id` FK, `monthly_amount`, `currency`, `status` (StrEnum: `ACTIVE`, `PAUSED`, `CANCELLED`), `next_charge_date`, `started_at`, `cancelled_at`.
- Link `Donation` rows generated by a sponsorship charge back to the `DogSponsorship` via a nullable `sponsorship_id` FK on `Donation`.
- Service: `create_sponsorship()`, `pause_sponsorship()`, `cancel_sponsorship()`, `list_sponsorships_for_donor()`.
- A scheduled ARQ job (follow the pattern in `src/pawguard/workers/jobs/scheduled_jobs.py` and registration in `src/pawguard/workers/arq_worker.py`) that runs daily, finds `DogSponsorship` rows where `next_charge_date <= today` and `status == ACTIVE`, creates a `Donation` row for each (reuse the existing `PaymentGateway` interface in `src/pawguard/core/payments/` — if the gateway isn't configured, just record a `PENDING`/manual-style donation like `make_donation` does), advances `next_charge_date` by one month, and triggers a notification to the donor (check `src/pawguard/modules/notifications/` for the existing notification-send pattern — reuse it, don't build a new channel).
- Router endpoints under `/donations/sponsorships` (self-service create/list for the donor, staff list-all under `donation:read`).

## 2. Donation: tax receipt generation

**Problem:** `AuthAuditEventType.DONATION_RECEIPT_ISSUED` is defined but never emitted. No receipt is ever generated.

**Build:**
- Use `reportlab` (already a dependency, used in `src/pawguard/modules/reports/renderers.py` — follow that PDF-generation pattern) to generate a simple tax-deductible receipt PDF: org name/address (stub values are fine, make them settings-configurable via `core/config.py`), donor name, donation amount/currency/date, transaction ID, a boilerplate tax-deductibility statement.
- Store the generated PDF via the existing storage module (`src/pawguard/modules/storage/service.py` — same `StorageService` you'd use for any file, folder `documents`).
- Trigger generation automatically when a donation transitions to `SUCCESS` (both the manual `make_donation` path and the online `verify_donation_payment`/webhook paths in `src/pawguard/modules/donation/service.py`) — emit `AuthAuditEventType.DONATION_RECEIPT_ISSUED` when done.
- New endpoint `GET /donations/{id}/receipt` returning a presigned download URL (reuse `StorageService.generate_presigned_download_url`).

## 3. Adoption: legal agreement/waiver/receipt generation

**Problem:** `AdoptionApplication.adoption_agreement_url` is a manually-set string field — PRR 3.7 wants this auto-populated when an application reaches `APPROVED`.

**Build:**
- reportlab-generated PDF: adopter name, dog details (registration number, name, breed), adoption fee (add a `fee_amount` field to `AdoptionApplication` if not present — check first), a standard liability-waiver clause, signature line placeholder, generated date.
- Trigger in `AdoptionService.update_application_status`/`update_application` (`src/pawguard/modules/adoption/service.py`) when status transitions to `APPROVED` — store via `StorageService` (folder `certificates`), set `adoption_agreement_url` to the resulting object key or presigned URL, audit-log it (reuse `AuthAuditEventType.ADOPTION_STATUS_CHANGED` metadata, or add a new `ADOPTION_AGREEMENT_GENERATED` event type).
- Endpoint `GET /adoptions/{id}/agreement` for download.

## 4. Foster: supply dispatch log

**Problem:** `FosterPlacement`/`place_dog()` only carries `dog_id`/`notes` — PRR 3.8 wants a dispatch log for supplies (food, crate, medication) sent with the dog.

**Build:**
- New model `FosterSupplyDispatch` (`src/pawguard/modules/foster/models.py`, alongside the existing `FosterProgressLog` that was just added — follow that exact pattern): `placement_id` FK, `dispatched_by_id` FK, `item_description` (or structured: `item_type` enum of Food/Crate/Medication/Other + `description` + `quantity`), `dispatched_at`.
- Service method `log_supply_dispatch(placement_id, payload, actor_id=...)`, `list_supply_dispatches(placement_id)`.
- Router: `POST /fosters/placements/{id}/supplies`, `GET /fosters/placements/{id}/supplies`.
- One migration, chained after whatever the current head is at the time you write it.

## 5. Inventory: `unit_cost` + medical/care linkage

**Problem:** `InventoryItem` has no cost field at all (blocks the "Inventory Valuation" report, which is why `reports/service.py::_inventory_report` can't compute a value). `InventoryMovement` isn't linked to what consumed the stock.

**Build:**
- Add `unit_cost: Mapped[float]` (Numeric(10,2), default 0.0) to `InventoryItem`.
- Add nullable `reference_type: Mapped[str | None]` (e.g. `"medical_treatment"`, `"daily_care_log"`) and `reference_id: Mapped[uuid.UUID | None]` to `InventoryMovement` — same freeform-reference pattern already used in `FinancialTransaction.reference_type`/`reference_id` (`src/pawguard/modules/finance/models.py`), for consistency.
- Wire it: when `MedicalService.record_treatment`/`prescribe_medication` (or wherever consumables get used — check `src/pawguard/modules/medical/service.py`) or `ShelterService.submit_daily_care_log` consumes inventory, they should call `InventoryService.record_movement(...)` with the reference set (this may require injecting `InventoryRepository`/`InventoryService` into those services — follow the same optional-constructor-param pattern used for `dog_repo` elsewhere, so it's backward compatible with existing tests that don't pass it).
- Update `reports/service.py::_inventory_report` to add a computed "Total Value" column (`quantity * unit_cost`) and a report-level total.
